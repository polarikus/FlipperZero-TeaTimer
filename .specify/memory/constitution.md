# Конституция Tea Timer

## Основные принципы

### I. Только внешнее приложение (FAP) для Flipper Zero

Продукт — внешнее приложение Flipper Zero, которое поставляется одним файлом `.fap` и
устанавливается с SD-карты. Дерево прошивки изменять, чтобы приложение заработало,
ЗАПРЕЩЕНО.

- Каждая возможность ДОЛЖНА быть реализована внутри каталога приложения; правки в
  `flipperzero-firmware/` запрещены.
- Файл `application.fam` ОБЯЗАН существовать и объявлять `appid`, `entry_point`,
  `apptype=EXTERNAL`, `requires`, `stack_size`, `fap_version` (строкой), `fap_category`,
  `fap_icon`.
- Во время работы разрешено использовать только сервисы, объявленные в `requires`.
- Разрешено подключать только публичные заголовки SDK; внутренние символы прошивки
  запрещены — их нет в таблице символов FAP, приложение не загрузится.

Обоснование: результат — съёмный самодостаточный артефакт; правка прошивки изменила бы
модель поддержки, порядок обновления и круг тех, кто может выпускать приложение.

### II. Только C и API Furi

Приложение пишется на C (C11 плюс расширения GNU, которые требует SDK) и работает только
через API прошивки Flipper.

- Всё взаимодействие с системой ДОЛЖНО идти через Furi API: примитивы `furi_*`,
  `view_dispatcher`, `scene_manager`, `gui/modules/*`, `storage/*`, `notification`,
  `dialogs`, `furi_hal_*`.
- Использование стандартной библиотеки C ОГРАНИЧЕНО операциями с известной границей и без
  блокировки (`snprintf`, `strtoul`, `memcpy`, `strlen`); `strcpy`, `sprintf` без
  ограничения длины и динамическое выделение памяти внутри draw/input-callback-ов
  запрещены.
- Стиль кода соответствует конвенциям прошивки: `snake_case` для функций, `PascalCase`
  для типов, префиксы `furi_`, отступ 4 пробела, форматирование `clang-format`.
- Диагностика идёт через `FURI_LOG_*` с коротким `TAG`, без `printf` в поставляемом коде.

Обоснование: FAP целиком загружается в RAM и линкуется к фиксированной поверхности API
прошивки; нестандартные конструкции C и блокирующие вызовы libc на этой платформе ломаются.

### III. Сначала готовые экраны и сервисы прошивки, потом свой код

Стандартные компоненты интерфейса прошивки ОБЯЗАНЫ использоваться раньше, чем пишется
собственная отрисовка.

- Каждый экран СНАЧАЛА сопоставляется с существующими модулями: `submenu`, `menu`,
  `file_browser`, `widget`, `popup`, `dialog_ex`, `text_input`, `number_input`,
  `byte_input`, `text_box`, `loading`, `empty_screen`, а также сервис `dialogs`.
- Собственный `View`/`ViewPort` с отрисовкой на `Canvas` разрешён, только если требование
  нельзя выполнить стандартным модулем (например, крупный шрифт отсчёта или инверсная
  плашка). Обоснование ОБЯЗАНО попасть в план или проектные заметки.
- Дублировать уже существующее поведение прошивки, реализованное модулем или сервисом, —
  нарушение, а не оптимизация.

Обоснование: переиспользованные компоненты уменьшают объём кода, расход RAM и стоимость
поддержки, а интерфейс остаётся привычным для устройства.

### IV. ufbt — единственный инструмент сборки (НЕ ПОДЛЕЖИТ ОБСУЖДЕНИЮ)

Сборка, проверка стиля кода, статический анализ, прошивка и отладка выполняются только
через `ufbt` из каталога приложения.

- Сборка: `ufbt`; принудительная пересборка: `ufbt FORCE=1`; подробный вывод:
  `ufbt VERBOSE=1`.
- Проверка и правка стиля: `ufbt format`; статический анализ: `ufbt lint`.
- Запуск и прошивка по USB: `ufbt launch`; база компиляции: `ufbt cdb`.
- Конфигурация проекта ОБЯЗАНА сохранять осмысленность `ufbt`, `ufbt format` и
  `ufbt lint`: исходники форматируются штатным `clang-format` SDK и остаются без
  предупреждений при предупреждениях SDK.
- Системы сборки из корня репозитория прошивки (`./fbt`, `scons`, `firmware.scons`) для
  этого проекта использовать ЗАПРЕЩЕНО.

Обоснование: `ufbt` фиксирует версии SDK и toolchain, поэтому локальная сборка совпадает
с тем, что исполнится на устройстве; вторая система сборки неизбежно приводит к расхождению
версий и невоспроизводимым сбоям.

### V. Ограниченная память и неблокирующий GUI-поток

Расход ресурсов ОБЯЗАН быть явным, ограниченным и симметричным.

- GUI-поток блокировать НЕЛЬЗЯ: никаких `furi_delay_ms`, синхронного ввода-вывода и
  долгих вычислений в draw/input/view-callback-ах. Время берётся из `furi_get_tick()` или
  из callback-а таймера.
- Крупные буферы живут в структуре приложения или в куче, но не на стеке; `stack_size`
  обосновывается и проверяется на устройстве.
- На каждый `*_alloc` ДОЛЖЕН быть `*_free`, на каждый `view_dispatcher_add_view` —
  `remove_view`, на каждый `furi_record_open` — `furi_record_close`, включая ветки ошибок
  и любой пользовательский выход.
- Файлы открываются только через `Storage` и закрываются на всех путях, включая
  неудачное открытие.
- Строки ограничены: `FuriString` для динамического текста, `snprintf` в буфер
  фиксированного размера для короткого текста.

Обоснование: внешнее приложение делит 256 КБ RAM с прошивкой, полностью выгружается при
выходе, а нарушение инварианта роняет сессию — утечки и блокировки видны пользователю.

### VI. Разработка с обязательным использованием скилла

Перед любым проектированием и любым изменением кода ОБЯЗАТЕЛЬНО изучается скилл проекта
по Flipper Zero.

- Перед планированием или реализацией агент ОБЯЗАН загрузить и соблюдать
  `.opencode/skills/flipper-zero-app-dev` (`SKILL.md` и нужные `references/*.md`).
- Утверждения об API ОБЯЗАНО проверять по справочникам скилла или по фактическим
  заголовкам SDK в `~/.ufbt/current/sdk_headers/`, а не по памяти и не по устаревшим
  примерам приложений.
- Быстро меняющиеся факты платформы (наличие модуля, устаревший API) ОБЯЗАНО проверять
  для используемой версии SDK.
- Если скилл и локальный пример приложения расходятся, верными считаются скилл и
  заголовки SDK, а пример — потенциально устаревшим.

Обоснование: API Flipper меняется между релизами, а решения этого проекта изначально
основаны на этом скилле; проверка по его справочникам исключает выдуманный или
устаревший API.

### VII. Язык артефактов: русский, кроме README

Язык артефактов фиксирован.

- Конституция, спецификации, планы, исследования, списки задач, чек-листы, quickstart,
  отчёты и любой вывод агента ОБЯЗАНЫ быть на русском языке.
- Единственное исключение — `README.md` в корне проекта: он ведётся на английском языке.
- Прочие файлы документации на английском создавать НЕЛЬЗЯ; при необходимости
  англоязычной публикации она делается вне репозитория.
- Идентификаторы в коде и сообщения логов остаются латиницей (требование синтаксиса C и
  ASCII-вывода), комментарии в коде — на русском.

Обоснование: команда работает с русскоязычными проектными документами, а публикуемый
артефакт — один англоязычный README; смешение правил делает спецификации нечитаемыми,
а README — непригодным для внешней аудитории.

### VIII. Обязательные юнит-тесты на устройстве (НЕ ПОДЛЕЖИТ ОБСУЖДЕНИЮ)

Юнит-тесты ОБЯЗАНЫ исполняться **на самом Flipper Zero**, а не на хосте: тестовый код
компилируется в состав FAP и запускается на устройстве. Образец организации — проект
`polarikus/flipper-zero_fn_tester` (каталог `unit_tests/`, minunit-раннер, реестр
наборов, CLI-команда запуска, агрегированный отчёт и проверка утечки кучи).

- Каждая функция, которую можно проверить без внешнего оборудования, ОБЯЗАНА иметь
  юнит-тест, выполняемый на устройстве: парсеры, валидаторы, арифметика, форматирование
  строк и времени, конечные автоматы, сериализация форматов файлов.
- Тесты живут в каталоге `unit_tests/` со своей структурой: `minunit.h`-совместимые
  макросы (`MU_TEST`, `MU_RUN_SUITE`, `MU_REPORT`, `mu_assert_*`), наборы тестов по
  модулям, `test_index.c` с реестром наборов и функцией регистрации.
- Запуск ОБЯЗАН быть доступен без перепрошивки и без пересборки: CLI-команда в сервисе
  `cli` (запись `RECORD_CLI`), вызываемая из `ufbt cli`. Регистрация — публичным API
  реестра CLI (`cli_registry_add_command_ex`), снятие — `cli_registry_delete_command`;
  устаревшие имена `cli_*` из compatibility-заголовка не используются. Имя любого
  символа ОБЯЗАНО сверять с `api_symbols.csv` и заголовками используемого SDK: символ
  без отметки `+` в таблице экспорта в FAP запрещён. Команда ОБЯЗАНА принимать
  необязательное имя набора, чтобы запускать один тест, и печатать отчёт: число тестов,
  утверждений и падений, время прогона, `Leaked:` по разнице `memmgr_get_free_heap()`
  до и после, итог `Status: PASSED` или `Status: FAILED`.
- Итог прогона ОБЯЗАН дублироваться на устройстве без чтения консоли: звуковое
  уведомление об успехе или ошибке (`sequence_success` / `sequence_error`).
- Тестовый код ОБЯЗАН быть исключён из обычного режима работы: регистрация команды и
  тестовые наборы включаются под `FURI_DEBUG` (или эквивалентным флагом сборки), не
  влияют на поведение приложения и не занимают RAM в релизном прогоне сверх самого
  кода.
- ОБЯЗАТЕЛЬНЫ тесты границ и ошибок, а не только «счастливого пути»: минимальные и
  максимальные допустимые значения, значения за границами, пустой ввод, отсутствующие
  поля, мусор после числа, превышение размера файла, дубликаты ключей.
- Тесты ОБЯЗАНЫ быть детерминированными: без зависимости от реального времени, от
  порядка запуска и от содержимого SD-карты, кроме случаев, когда тест сам готовит
  данные через `Storage` во временном каталоге и убирает их за собой.
- Каждое изменение ОБЯЗАНО сопровождаться прогоном полного набора тестов на устройстве
  с результатом `Status: PASSED`; падение хотя бы одного теста блокирует слияние.
- Каждая найденная дефектная ситуация ОБЯЗАНА получить регрессионный тест, который
  воспроизводит ошибку до исправления.
- ЗАПРЕЩЕНО: тесты-заглушки без утверждений, отключённые или «пропущенные» тесты,
  тесты, которые нельзя запустить на устройстве, и подмена проверки на устройстве
  прогоном на хосте.
- Прогон на хосте (обычный `cc`) допускается только как вспомогательный приём для
  быстрой отладки; он НЕ считается выполнением этого принципа и не освобождает от
  обязательного прогона на устройстве.

Обоснование: приложение исполняется на MCU с другим размером указателей, другой
арифметикой (`int`, выравнивание), ограниченной кучей и реальным API Furi; ошибки
парсинга, переполнения буферов и утечки проявляются именно там. Прогон на устройстве
проверяет то, что действительно поставляется пользователю, а CLI-отчёт даёт
автоматизируемый и воспроизводимый результат.

## Технические ограничения и лимиты платформы

Эти лимиты жёсткие и действуют для каждой возможности.

| Ограничение | Значение |
|---|---|
| Микроконтроллер | STM32WB55, Cortex-M4F, 256 КБ RAM, 1 МБ flash |
| Экран | 128×64, 1 бит на пиксель, шрифты `FontPrimary`/`FontSecondary`/`FontBigNumbers` |
| Стек приложения | обычно 1–2 КБ на поток; обосновывается для каждого приложения |
| Хранение данных | только SD-карта через `Storage`; данные приложения — `APP_DATA_PATH(...)`, ассеты — `APP_ASSETS_PATH(...)` |
| Модель исполнения | FAP загружается в RAM целиком; нет отображения в память и ленивой загрузки |
| Модель отказа | `furi_check`/`furi_crash` завершает приложение; проверки инвариантов — принятый способ их соблюдения |
| Базовый язык | C11 плюс расширения GNU, поддерживаемые toolchain SDK |

Дополнительные правила:

- Строки интерфейса на устройстве ОБЯЗАНЫ быть на английском в ASCII (кириллицу штатные
  шрифты не отображают), короткими и помещающимися в 128×64. Это ограничение платформы, а
  не языковая политика из принципа VII.
- Аппаратные ресурсы (serial, IR, Sub-GHz, NFC, iButton) захватываются и освобождаются
  парами, с `*_reset`/`*_deinit` при освобождении.
- Сохраняемые форматы файлов — часть публичного контракта: изменение, ломающее существующие
  файлы, требует обоснования на уровне конституции и заметки о миграции.
- Поведение памяти и стека ОБЯЗАНО проверяться на устройстве через `ufbt cli` (`free`,
  `top`) до того, как возможность считается готовой.
- Тестовая CLI-команда и тестовые наборы ОБЯЗАНЫ собираться в FAP, но активироваться
  только под `FURI_DEBUG`; в обычном режиме приложение не должно печатать в консоль и
  не должно зависеть от подключённого USB.

## Процесс разработки и контрольные точки качества

Каждое изменение ОБЯЗАНО пройти следующие проверки по порядку.

1. **Спецификация**: изменение поведения описано в `specs/<feature>/spec.md`; код
   пишется только после согласования спецификации.
2. **Проектирование**: в `plan.md` зафиксированы сопоставление экранов модулям
   (принцип III), бюджет памяти и стека (принцип V) и использование `ufbt`
   (принцип IV).
3. **Ревью**: проверка кода явно проходит по всем принципам I–VIII, с особым вниманием к
   парности ресурсов, блокировкам GUI-потока и наличию юнит-тестов.
4. **Сборка**: `ufbt` собирает без предупреждений; `ufbt format` не даёт диффа;
   `ufbt lint` не оставляет неразобранных замечаний.
5. **Тесты**: `ufbt launch` (или `ufbt`) собирает FAP с тестовым модулем, затем тесты
   запускаются на устройстве одной CLI-командой через `ufbt cli`; отчёт ОБЯЗАН
   заканчиваться `Status: PASSED` без падений и без утечки кучи. Отсутствующий тест для
   изменённой логики или падение хотя бы одного теста блокирует слияние.
   Поведение, проверяемое только вручную, ОБЯЗАНО иметь описанный сценарий в
   `quickstart.md`.
6. **Устройство**: `ufbt launch` запускает приложение; BACK корректно выходит с любого
   экрана; звук, вибро и принудительная подсветка не остаются после выхода; `free` после
   выхода совпадает с исходным значением; отчёт прогона тестов сохранён в описании
   изменения.
7. **Документация**: спецификации и планы на русском, `README.md` в корне на английском,
   строки интерфейса — английский ASCII.

Сложность сверх этих проверок ОБЯЗАНА быть обоснована в разделе Complexity Tracking плана
с указанием отвергнутой более простой альтернативы.

## Управление

- Конституция главнее других практик проекта. При конфликте с `AGENTS.md`, скиллом или
  локальным примером приложения действует конституция; при её молчании применяются
  `AGENTS.md` и скилл проекта.
- Правки вносятся отдельным изменением этого файла вместе с комментарием
  `Sync Impact Report`, где указаны изменение версии и изменённые разделы. Перед коммитом
  правленой конституции отчёт ОБЯЗАНО удалить.
- Версионирование следует семантическому версионированию governance:
